01 How the data flows

Five tabs, two SQL engines, one table

Every page ultimately reads the same option_oi_snapshots hypertable, but through two fundamentally different query engines. That single fork is the root of most cross-page number differences.

Dotted edges are secondary lookups (spot / ATM only). Replay reads one frames payload and derives everything client-side.

Engine A · latest snapshot

Takes the single most-recent row per (strike, option_type) with ts ≥ 09:15 today; change = now − a session-floored baseline (per-strike clamp). Emits per-strike changes + level totals.

  • /api/oi-change · /api/multi-timeframe
  • /api/option-chain-full · /api/replay

Engine B · bucketed levels

Buckets with gap-fill and carries the last-known OI forward (locf). Emits absolute levels per bucket only — "change since open" is computed on the frontend from the first returned bucket.

  • /api/oi-timeseries · /api/ratio-timeseries

04 Fixed this pass

The Side rule + five consolidations

Side Dominant-side rule → smaller signed value

The finalized spec: Side = the side whose signed OI change is the SMALLER (lower) value; Neutral on a tie. The magnitude-normalized ratio text is unchanged. Because callPutRatio() is the single source, this propagates to Multi-TF, the OI Change hint, and Replay at once.

side = |ΔCall| > |ΔPut| ? CALL : PUT → side = ΔCall < ΔPut ? CALL : PUT
frontend/src/utils/ratio.ts · e.g. Full Day +45.90L / +1.56Cr now reads Call (was Put)

F1 One strike window

Multi-TF now sends the effective window (ATM±(N−1)) to the backend, so its summed strikes match its own footer label and the Charts / Ratio / OI-Change windows. Sentinels pass through (0 → ATM only, "All" → full chain).

frontend/src/pages/MultiTimeframePage.tsx → effectiveAtmWindow(atmWindow)

F2 One PCR

PCR is now Put OI ÷ Call OI on levels everywhere (matches the backend). The change-based directional read still lives in the "Ratio" tile + dominant Side, so nothing is lost.

frontend/src/components/KPIBar.tsx

F3 One ATM

A single atmRound(spot, step) = round(spot/step)·step — identical to the backend atm_strike — now centres every client window and every ATM label.

frontend/src/utils/oiStrikeWindow.ts · KPIBar · ChartsPage

F4 One formatter set

Three local compact/compactNum copies (and two inline fmt2) collapse into utils/num.ts. Cr / L / k renders identically on every tab.

num.ts ← KPIBar · OICandleChart · OIChangeChart · MultiTimeframePage · RatioChartPage

F5 One Δ colour convention

Positive change = green, negative = red, the same for Call and Put — shared from utils/ui.ts (changeColor, plus sideColor/sideLabel). The inverted KPIBar branch is gone. Chosen to match the Multi-TF page already in production; flip if the "call-writing = red" convention is preferred instead.

frontend/src/utils/ui.ts ← KPIBar · MultiTimeframePage · ReplayPage

05 Not touched — on purpose

Deferred (architectural)

  • Unify the two query engines. Making Ratio/Charts and Multi-TF/OI-Change read OI through one engine is a backend rewrite with real regression risk — worth doing deliberately, not folded into this pass.
  • Ratio-timeseries default window. Defaulting to the full stored strike range (which can include stale prior-day strikes) should become ATM±N — but that shifts existing Ratio-page numbers, so it needs sign-off.
  • Hidden-dashboard parity. The isolated /hidden app keeps its own signed ratio + formatters; bringing it onto the shared helpers is a separate task.

By design (documented, not bugs)

  • Multi-TF "Ratio" means two things. The header ratio is of levels; the per-row ratio is of changes. Same word, deliberately different metric.
  • Intraday vs Full Day Δ. Intraday change is incremental against a timeframe baseline; Full Day is cumulative from 09:15.
  • /api/spot returns null off-symbol. Spot is served only for the active symbol — expected, not a data gap.
  • Ratio text vs Side can look opposite. A row may read Ratio 1 : 3.41 yet Side Call — an intentional consequence of the new signed-value rule.
